Keep these optimizations

The database is not starting from zero. These existing choices reduce work or protect correctness.

Cursor pagination already exists

Order pages use stable sort keys and an ID tie-breaker, fetching one extra row to check for a next page. Default unpaginated lists are capped at 200; explicit pages at 500.

Search has purpose-built indexes

GIN trigram indexes support partial text searches. Parcel search text has a trigger to refresh it when a linked party’s search fields change.

Dashboard work is already consolidated

Overview metrics share a conditional aggregate, and tab counts use groupBy. The existing trend query bounds creation, pickup and delivery events independently.

Recent history fetches are bounded

Order list remarks and status history each use take: 1; parcel/time indexes support those lookups. This is not a proven per-order application N+1 loop.

Writes have practical limits

Bulk creation caps batches at 100 and runs five orders at a time. Webhook delivery sweeps take 100 rows with ten delivery workers.

Financial and event integrity matters

Journal entries have a unique source/event key. Webhook rows are enqueued in the same transaction as status changes; keep this durable outbox.

Budget connections across every app process

Implemented guard

The code permits up to 60 database connections per process by default. The local database allows 100 connections in total. Starting more processes does not create more database capacity.

Before · audited behavior

Each processIndependent pool of 60
More processesPotential demand multiplies
DatabaseOne shared limit

After · implemented locally

Capacity budgetReserve admin/job headroom
Per-process shareDivide by process count
MonitorWaits, latency, CPU

Why this helps: A connection budget avoids oversubscription. Faster queries and short transactions often matter more than a larger pool.

Implementation, evidence and checks

Implemented: pool sizes/timeouts are validated as integers at startup. Optional DB_CONNECTION_BUDGET and DB_APP_PROCESSES must be supplied together; startup rejects a pool size multiplied by process count that exceeds the app’s total budget. Operators must include workers and rolling-deployment overlap.

With PERFORMANCE_TIMING=true, operator logs include numeric pool snapshots at request start/finish: maximum, total, idle and waiting connections. These point samples are not peak waits or wait durations and are not exposed in API payloads.

The default remains 60 connections per process. The idle-transaction backstop now travels in the connection startup packet, avoiding a race with the first Prisma query. It is not a statement timeout. No production capacity setting was changed.

Correctness comes first

  • Same order IDs, sort order, totals and bank/contact visibility for each permitted role.
  • No other vendor’s orders or money in dashboard or Partner API responses.
  • Nepal date boundaries, soft deletes and repeated history events stay correct.
  • Settlement cancellation, partial payments and collected-cash calculations stay correct.

Define success before rollout

  • Measure p50 (typical) and p95 (slower-end) API time separately for cache hits and misses.
  • Compare rows read, buffers touched, sort spills and data transferred where observable.
  • Track order-create/status-update time as well as read improvements; indexes cost work on writes.
  • No increase in failures or pool waits, and a documented way to revert the candidate.
Operational concerns that should not be hidden by tuning

Transactions: preserve atomic finance writes and the transactional webhook outbox. Do not keep a database transaction open during a remote network call. Existing bounded bulk writes and sweep workers are useful limits; evaluate duration under representative concurrency rather than removing them.

Multiple webhook workers: the current Redis lock and process-local in-flight guard reduce overlap. Redis-error fallback runs anyway. If scaling to multiple processes, evaluate a database claim/lease strategy with safe expiry; keep delivery IDs for retry deduplication. This is a conditional concurrency improvement, not an observed local failure.

Backup and retention: nightly pg_dump-to-S3 and restore scripts exist. Their scheduling, successful restore history and point-in-time recovery were not verified. Test a restore on a disposable stack. Plan retention for notifications, webhook payloads and audit history using business requirements; never delete financial history merely to improve a benchmark.

Index hygiene and drift: local idx_parcels_carrier_id is outside the reviewed current Prisma schema/migration definitions. Document its origin before touching it. Some leading-prefix indexes may overlap a primary/composite key (for example branch settlement items by settlement_id); inspect usage and constraints over a representative period before proposing removal. Low scan counts alone do not prove an index is useless. No indexes were removed here.

The source changes and migrations are implemented in this checkout. These six index migrations succeeded on localhost; production deployment remains separate.

Implemented migrations and deployment rules
-- One statement per migration: PostgreSQL concurrent builds cannot run in a
-- transaction. Keep this separate from other DDL and do not add BEGIN/COMMIT.
CREATE INDEX CONCURRENTLY "idx_parcels_vendor_order_number_id"
ON "public"."parcels" ("vendor_id", "order_number" DESC, "id" DESC);

-- Pair with the native parcel_status predicate in dashboard.ts.
CREATE INDEX CONCURRENTLY "idx_parcel_history_status_created_parcel"
ON "public"."parcel_status_history" ("new_status", "created_at", "parcel_id");

-- The primary key starts with settlement_id; this covers the reverse lookup.
CREATE INDEX CONCURRENTLY "idx_settlement_items_cod_settlement"
ON "public"."settlement_items" ("cod_collection_id", "settlement_id");

CREATE INDEX CONCURRENTLY "idx_settlements_vendor_created_id"
ON "public"."settlements" ("vendor_id", "created_at" DESC, "id" DESC);

CREATE INDEX CONCURRENTLY "idx_settlements_rider_created_id"
ON "public"."settlements" ("rider_id", "created_at" DESC, "id" DESC);

-- Keep idx_notifications_user_read for unread counts; this covers the feed.
CREATE INDEX CONCURRENTLY "idx_notifications_user_created_id"
ON "public"."notifications" ("user_id", "created_at" DESC, "id" DESC);

Each migration contains one concurrent index build, with no explicit transaction. The current Prisma deployment runner executed these exact files successfully on local PostgreSQL 18.4. Compose targets PostgreSQL 16, so check representative staging on the deployment version.

Concurrent builds need resources and can leave an invalid index on failure. Verify definitions and pg_index.indisvalid; do not skip a failed build with IF NOT EXISTS. Preserve business rows and pre-existing indexes.

Read the staged deployment, failure recovery and rollback procedure. Production was not accessed or deployed.

Try explaining this to a teammate

There are 200,000 orders. Your page needs 20 orders for one vendor. Why can the page still require lots of work?

Reveal the explanation

The database may filter or sort many rows to find the right 20. It may also count all matching rows, fetch large related records, and repeat that work after a cache miss. A small response is not proof of a small query.

A parcel was created last month but delivered today. Should a seven-day delivery graph include it?

Reveal the explanation

Yes. Filter by the delivery event’s timestamp for deliveries. Filtering only by the parcel’s creation time would lose it. This is why the existing trend query bounds each milestone separately.

Beginner glossary
Query
A request to find, count or change stored records.
Index
A maintained lookup guide. It can help reads, but uses storage and must be updated during writes.
Composite index
A guide sorted by several fields in order, such as vendor first and newest order next.
Partial index
A guide containing only rows matching a fixed rule, such as parcels that are not trashed.
Cursor pagination
Continue after the previous page’s last sort key, like a bookmark.
Offset pagination
Skip a number of earlier rows to reach a page. Deep pages may require more skipped work.
Foreign key
A rule connecting records, such as a settlement item to its cash collection.
Transaction
A group of database actions that succeed together or roll back together.
Cache invalidation
Removing a saved answer after its underlying records change.
Query plan
The steps PostgreSQL chooses to find records: scan, filter, join, sort and aggregate.
Statistics / ANALYZE
Estimates used to choose plans; ANALYZE refreshes planning information.
Vacuum
Maintenance that reclaims reusable space from old row versions and supports healthy database operation.
p50 / p95
Half of measured requests are at or below p50; 95% are at or below p95. Report the workload and sample count too.
Synthetic benchmark
A test with made-up records. Useful for comparing approaches; it cannot promise live website speed.
