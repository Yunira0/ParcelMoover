A page can wait in more than one place

A slow first visit does not automatically mean the database is slow. There are downloads and server work along the way.

Download codeThe browser gets the page instructions
Ask the serverAPI request: a message asking for data
Read the databaseA query finds and counts records
Show the resultThe page fills in its content

Simplified illustration. Some of this work can overlap. Later visits can reuse downloaded code, which is one reason they may feel quicker.

A safer file-reading step

Selecting another file clears the old draft. Submission stays disabled while reading, and a delayed result from an older file cannot replace the newer selection.

The useful behavior stays the same

The file format, row validation and import request stay the same. For bulk orders, a CSV file can be read without downloading the spreadsheet engine.

Give the dashboard less history to count

A query is a question sent to the database. The dashboard asks how many orders were created, picked up or delivered on each day of its 7-day or 30-day chart.

Before Count across all history

Evaluate the daily counts against every parcel the user is allowed to see, including old history.

After Filter relevant events first

Evaluate the same counts only for parcels created, picked up or delivered during the displayed period.

What stayed accurate

Lifetime totals and cash-on-delivery figures keep their original basis. Vendor/staff access, deleted-order rules and Nepal day boundaries are preserved. No database index was added.

Add a stopwatch to find the real wait

The server now has an optional timing switch. It reports how long an API request and its database operations take, so the next improvement can target the part that is actually slow.

Browser asks for dataFor example, dashboard numbers
Server measures its workRequest · authentication · database operations
Developer reads the timingsIn response headers and server logs

Before

This dedicated request-timing switch was absent. The complaint alone could not identify whether downloads, authentication or database work caused the wait.

After

Enable PERFORMANCE_TIMING=true and restart the server to collect timings. It covers dashboard APIs and the vendor Partner API. It is off by default.

API time
How long the server takes up to sending response headers.
Authentication time
Time spent checking who is making the request.
Database time
Time spent in database operations, including client and connection overhead.
Operation count
How many logical database operations ran.

These timings can overlap, so do not add them together. The database measurement includes time outside SQL, the commands sent to the database. The operation count is not an exact count of those commands. Logs omit SQL, passwords, request data and user/vendor identifiers.

The live website still needs a before-and-after check

These improvements are in the local code. They have not been deployed. We have not yet measured logged-in page speed or inspected the live database’s step-by-step plans for finding and counting records.

  1. Measure the first and repeat visit. Check dashboard, orders, finance, reports and settings for the main user roles.
  2. Find where the wait happens. Separate code downloads from API waits. Use the optional timings to guide database, connection-pool and cache checks.
  3. Roll out and compare. After a deployment, compare multiple live samples before claiming an improvement for all pages.

Beginner glossary
First visit
The browser may need to download files it does not already have. A later visit can reuse them.
API
The way the browser asks the server for data or an action.
Database
The organized storage for orders, vendors, delivery events and other records.
Query
A request to find, count or change database records.
On-demand loading
Download a tool when its task starts, instead of whenever the page opens.
Cache
A saved copy that can be reused. It can make repeat requests quicker.
Connection pool
A set of reusable connections between the server and database. Requests may wait if they are all busy.
Index
A database lookup aid, similar to a book’s index. Useful indexes depend on which queries are slow.
Synthetic benchmark
A speed test using made-up data. It helps compare approaches but does not prove production speed.
Loading budget
A limit for the amount of code a checked page downloads, helping catch future increases.
What we observed on the public live site

Two requests for the public login page received the first HTML byte in 373–467 ms. One already-cached JavaScript file responded in 16 ms; six cache-miss files started responding in 266–537 ms.

These were a few sequential command-line samples, not a browser page-load measurement or a reliable average. The live build differed from this checkout. The browser was signed out, and local PostgreSQL was stopped, so protected API and real database timings were not captured.

Asset files already used long-lived caching. This task did not change production data, cache lifetimes, pool settings or database indexes.

Where the changes live in the project
  • Load the spreadsheet tool later: client/src/pages/vendor/BulkOrderPage.tsx, client/src/pages/DeliveryRatesImport.tsx and client/src/pages/settings/DestinationsImport.tsx.
  • Filter the trend query: server/src/services/orders/dashboard-trend.ts and dashboard.ts in the same folder.
  • Measure requests: server/src/lib/requestPerformance.ts, Prisma integration and the session/API-key authentication wrappers.
  • Catch future regressions: focused server tests, client/scripts/check-loading-budgets.mjs, the page-cost report and the synthetic query benchmark.
  • Explain the operator switch: the server environment example, Partner API guide, interactive console and generated API reference.
